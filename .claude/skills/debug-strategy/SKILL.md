# 调试策略选择

根据问题特征选择调试方法，避免无效的代码推理。

## 直接理解代码找问题的情况

| 场景 | 特征 |
|------|------|
| 明确错误信息 | TypeError、编译错误、异常堆栈 |
| 代码路径简单 | 单一函数、逻辑清晰 |
| 测试能复现 | 单元测试失败，可在测试中调试 |
| 逻辑错误 | 条件判断、边界条件、算法问题 |

## 必须加日志的情况

| 场景 | 特征 |
|------|------|
| **测试通过但实际失败** | 说明测试没覆盖真实场景 |
| 涉及外部协议 | PS 协议消息格式、API 响应 |
| 多组件交互 | 数据在多个模块间传递 |
| 运行时数据未知 | 不确定实际值是什么 |

## 经验教训: v1.2.12 Multi Battle p4 Slot 问题

**错误做法**:
1. 测试用 `p4a` 发送消息
2. 代码用 `p4a` 获取
3. 测试通过 ✓
4. 用户反馈实际不工作 ✗
5. 继续猜测代码问题...

**正确做法**:
1. 用户说"测试通过但实际不工作"
2. **立即加日志观察实际数据**
3. 日志显示: `handleBoost for p4b` vs `boostKey=p4a`
4. 问题立即暴露: PS 协议用 `p4b`，代码用 `p4a`

## 关键信号

当测试和实际表现不一致时，**优先加日志看真实数据**，而不是继续推理代码。

## 调试流程

```
1. 确认问题类型（参考上方表格）
2. 如果是"直接理解"类型 → 阅读代码、分析逻辑
3. 如果是"必须加日志"类型 →
   a. 在关键路径添加日志
   b. 复现问题，收集日志
   c. 对比预期值和实际值
   d. 定位差异点
4. 如果不确定问题在哪个模块 → git bisect 或注释一半代码二分定位
5. 如果难以稳定复现 → 构建最小测试用例，逐步添加组件直到问题出现
6. 修复并验证
```

## 常见陷阱

- **过度推理**: 在脑中模拟代码运行而不实际观察 → 加日志
- **测试覆盖假象**: 测试通过 ≠ 功能正确，测试本身可能有错误假设
- **改了代码没效果**: 检查是否重新编译（`npm run build`）、缓存问题
