# v1.2 需求文档 - 多人组队对战 NPC

## 目标

实现两名玩家组队对战 NPC 双打的功能，复用 PS 原生 Multi Battle 机制和现有 NPC AI 系统。

---

## 背景

### 用户需求

用户希望能够与好友组队，一起挑战 NPC 对战。这需要：
- 两名玩家在同一房间协作
- 各自控制一只精灵
- NPC 保持双打的协作能力

### PS 原生 Multi Battle

Pokemon Showdown 已有 `gameType: 'multi'` 支持 4 人对战：

```
              Team 1                    Team 2
        ┌─────┐  ┌─────┐          ┌─────┐  ┌─────┐
        │ p1a │  │ p3a │          │ p2a │  │ p4a │
        │(3只)│  │(3只)│    VS    │(3只)│  │(3只)│
        └─────┘  └─────┘          └─────┘  └─────┘
```

**关键特性**:
- p1+p3 共享 sideConditions（光墙、反射壁等）
- p2+p4 共享 sideConditions
- 每个玩家只能换自己的后备精灵
- 原生邀请机制 (`/invitebattle`, `/acceptbattle`)

---

## 功能需求

### FR1: 格式定义

**描述**: 创建新格式 `[Gen 9] National Dex Multi`

**细节**:
- `gameType: 'multi'`
- `Max Team Size = 3`
- 复用 Standard Doubles 规则
- 复用 National Dex 规则

**验收标准**:
- [ ] 格式可在对战中选择
- [ ] 每人最多 3 只精灵
- [ ] 禁止项与 National Dex Doubles 一致

---

### FR2: 房间创建流程

**描述**: 实现 NPC Multi 对战的房间创建

**命令**: `/npc multi [npcId]`

**流程**:
1. 玩家1 执行 `/npc multi gymbrock`
2. 创建房间，玩家1 加入 p1，NPC 占据 p2 和 p4
3. 显示邀请表单（只显示 p3 邀请选项）
4. 玩家1 执行 `/invitebattle @玩家2, p3`
5. 玩家2 执行 `/acceptbattle`，提交队伍
6. 4 人齐备，战斗开始

**验收标准**:
- [ ] `/npc multi` 命令可用
- [ ] NPC 自动占据 p2 和 p4 位置
- [ ] 邀请表单只显示 p3 选项
- [ ] 玩家2 加入后战斗自动开始

---

### FR3: NPCManager 协调器

**描述**: 统一协调 p2 和 p4 的 AI 决策

**核心功能**:
1. 接收并缓存 p2 和 p4 的 request
2. 等待两边都准备好后统一决策
3. 构建虚拟双打状态（合并 p2+p4 视角）
4. 复用现有评分系统进行决策
5. 分别发送 p2 和 p4 的选择

**Request 同步机制**:

| 情况 | 处理方式 |
|------|---------|
| 两边都需要选择 | 等待同步后统一决策 |
| 只有一边需要选择 | 单独处理该 side |
| forceSwitch | 立即处理，不等待另一边 |
| wait | 标记并跳过 |

**验收标准**:
- [ ] p2 和 p4 的决策协调一致
- [ ] 不会出现互相攻击队友的情况
- [ ] forceSwitch 能立即响应
- [ ] 复用现有双打队友检查逻辑

---

### FR4: NPC 队伍配置

**描述**: 支持配置 NPC 在 p2/p4 位置的精灵分配

**方案**: 在现有 doubles 队伍文件中添加 `slot` 字段

```json
[
  { "name": "Tyranitar", "species": "Tyranitar", "slot": "p2" },
  { "name": "Excadrill", "species": "Excadrill", "slot": "p4" },
  { "name": "Landorus-Therian", "species": "Landorus-Therian", "slot": "p2" },
  { "name": "Garchomp", "species": "Garchomp", "slot": "p4" },
  { "name": "Ferrothorn", "species": "Ferrothorn", "slot": "p2" },
  { "name": "Rotom-Wash", "species": "Rotom-Wash", "slot": "p4" }
]
```

**验收标准**:
- [ ] 支持 `slot: "p2"` 和 `slot: "p4"` 字段
- [ ] 无 slot 字段时向后兼容普通双打
- [ ] p2 和 p4 各分配 3 只精灵

---

### FR5: 玩家队伍

**描述**: 玩家使用 teambuilder 中的队伍

**细节**:
- 玩家1: 使用当前选中的队伍
- 玩家2: 接受邀请时通过 teambuilder 提交队伍

**验收标准**:
- [ ] 玩家1 的队伍从 teambuilder 读取
- [ ] 玩家2 接受邀请时可以选择队伍
- [ ] 队伍验证通过 National Dex Multi 规则

---

### FR6: 胜负判定

**描述**: 使用 PS 原生 Multi Battle 胜负判定

**规则**:
- 玩家侧 (p1+p3) 共 6 只全灭 → 玩家输
- NPC 侧 (p2+p4) 共 6 只全灭 → 玩家赢

**验收标准**:
- [ ] 无需额外实现，PS 原生行为
- [ ] 胜负结果正确显示

---

## 非功能需求

### NFR1: 性能

- NPCManager 决策时间 < 3s（需等待两边 request）
- 房间创建时间 < 3s

### NFR2: 可维护性

- NPCManager 独立模块，不影响现有单打/双打 AI
- 复用现有评分系统，不重复实现

### NFR3: 用户体验

- 邀请流程清晰，玩家2 能理解如何加入
- 战斗中两名玩家都能看到完整战场

## 范围限制

### v1.2 不包含的内容

| 功能 | 原因 | 备注 |
|------|------|------|
| 物种不重复验证 | 用户自觉遵循 | 可后续添加 |
| 随机组队匹配 | 复杂度高 | 未来版本 |
| 玩家 vs 玩家 Multi | 当前只支持 vs NPC | 可扩展 |

### 技术限制

- 不修改 PS sim 核心代码
- 不引入非对称 gameType
- 不修改客户端

## 风险与缓解

### 风险 1: NPCManager 同步复杂性

**风险**: p2 和 p4 的 request 时序复杂，可能导致死锁或超时。

**概率**: 中
**影响**: 高

**缓解措施**:
- 设置超时机制，单边超时则单独决策
- 详细日志记录 request 时序
- 单元测试覆盖各种时序场景

### 风险 2: 邀请流程体验

**风险**: 玩家2 不清楚如何加入对战。

**概率**: 中
**影响**: 中

**缓解措施**:
- 清晰的邀请提示信息
- 文档说明完整流程
- 考虑添加快捷邀请链接

### 风险 3: 队伍配置不平衡

**风险**: p2 和 p4 的精灵配置不合理导致 NPC 表现不佳。

**概率**: 低
**影响**: 中

**缓解措施**:
- 提供队伍配置建议
- 测试多种配置组合
- slot 字段设计便于调整
